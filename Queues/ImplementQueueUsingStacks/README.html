Implement Queue Using Stacks

Day 8 · Topic: Queues · Daily DSA Challenge

Difficulty: Easy Pattern: Two Stacks / Amortised Analysis Time: O(1) amortised Space: O(n)

🧩 The Problem

Build a FIFO queue using nothing but stack operations — push, pop, top and isEmpty. No arrays with indices, no linked lists, no built-in deque. Only stacks.

You must support four operations:

OperationMeaning
push(x)Add x to the back of the queue
pop()Remove and return the element at the front
peek()Return the front element without removing it
empty()Is the queue empty?
push(1)   -> queue: front [1] back
push(2)   -> queue: front [1, 2] back
push(3)   -> queue: front [1, 2, 3] back
peek()    -> 1        // oldest element, not the newest
pop()     -> 1        // queue: front [2, 3] back
push(4)   -> queue: front [2, 3, 4] back
pop()     -> 2
pop()     -> 3
pop()     -> 4
empty()   -> true

The whole difficulty is the mismatch: a stack hands back the newest item, a queue must hand back the oldest one. We need to flip the order somewhere.

📖 The Story

Imagine a narrow kitchen with a stack of dirty plates. Plates go on top, and you can only ever take the top one off — that is a stack. But the house rule is fair play: the plate that has been waiting the longest must be washed first. The plate at the very bottom. Awkward.

Here is the trick. Keep two piles on the counter: an IN pile and an OUT pile. Every dirty plate that arrives simply goes on the IN pile. No thinking, no shuffling, instant.

When it is time to wash one, look at the OUT pile first. If it has plates, wash the top one — done. If the OUT pile is empty, then move every plate from IN to OUT, one at a time. Because you take from the top of IN and place on the top of OUT, the pile arrives upside down: the oldest plate, once buried at the bottom, is now sitting proudly on top. Wash it.

The one rule you must never break: only refill OUT when it is completely empty. If you dump fresh plates on top of a half-used OUT pile, newcomers jump the queue and fairness is destroyed.

Does all that carrying make it slow? Look closer. Each plate is carried from IN to OUT exactly once in its whole life. It is placed once, moved once, washed once. Three touches per plate, no matter how the work is spread out. One unlucky wash may involve hauling twenty plates — but the next nineteen washes are then free.

That last paragraph is amortised analysis. A single pop() can cost O(n) in the worst case, yet any sequence of n operations costs O(n) in total, so the average cost per operation is O(1). Averaged over time, not averaged over lucky inputs — this is a guarantee, not a hope.

The lazy alternative is to pay up front: reverse the whole stack on every single push so the front is always on top. That works too, but it makes push O(n) and wastes effort re-reversing elements nobody asked for yet. Doing work only when it is actually needed is almost always the better deal.

🌍 Real-Life Example

A printer spooler. Documents arrive in bursts and must print in the order they were sent. The receiving buffer collects jobs as fast as they come (the IN pile) while the print engine drains a prepared batch (the OUT pile). Nobody reorders the batch mid-print — a new burst waits for the current batch to finish.

Customer support tickets. New tickets land in an inbox instantly with no sorting. Periodically an agent pulls the whole inbox into a working list, oldest-first, and works through it. Fresh tickets pile up in the inbox meanwhile — they do not cut in front of someone who has been waiting since morning.

Undo and redo. The same two-pile idea, one step sideways: actions move between two stacks and the direction of travel decides whether you are undoing or redoing.

🔀 Logic Flow Chart

Pushes never touch the OUT stack. Transfers happen only when OUT has run dry — that single condition is what preserves FIFO order.

⚙ Approaches Compared

ApproachTimeSpaceIdea
Costly Push (brute force)push O(n), pop/peek O(1)O(n)On every push, empty the stack into a helper, drop the newcomer at the bottom, pour everything back. The front always sits on top.
Two Stacks, lazy transfer (optimised)push O(1), pop/peek O(1) amortisedO(n)Push onto IN. Refill OUT from IN only when OUT is empty; the pour reverses the order exactly once.

Why lazy wins

Each element crosses from IN to OUT at most once ever. Any sequence of n operations does at most 2n stack moves, so the amortised cost per operation is a constant.

Trade-off

One individual pop can still cost O(n). If you need a hard worst-case bound per call — a real-time system, say — the costly-push version gives you O(1) pops at the price of O(n) pushes.

Edge cases worth remembering: pop() or peek() on an empty queue must fail loudly — check both stacks, not just one; empty() is true only when IN and OUT are both empty; and interleaving pushes with pops is the case that actually catches bugs — push 1,2, pop, push 3, pop, pop should yield 1, 2, 3.

💡 Where This Pattern Shows Up Next

The mirror problem is Implement Stack Using Queues, which is instructive precisely because the trick does not flip around neatly. The amortisation argument here is the same one behind dynamic array resizing (why ArrayList.add is O(1) amortised despite occasional doubling) and behind the two-stack Min Queue. The two-container idea reappears in Undo/Redo, in double-ended sliding windows, and in BFS with a frontier and a next-frontier.
